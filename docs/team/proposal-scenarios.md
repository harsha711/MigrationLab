## What changed
- **`migproto/scenarios.py` (new):** a registry of schema changes under review. Each scenario defines:
  - its app variants: `apply` is the naive Django migration, `state_only` uses `SeparateDatabaseAndState`
  - the cases to run, the preserved and not-null columns, and the columns expected after contract

  `rename-note` is the default and keeps its original checks verbatim (`rename_hooks`).
- **`plans.py`:** `deploy_new` may set `"migration": "apply" | "state_only"` (default `state_only`). With `apply`, the expand and contract stages are optional, which allows `[deploy_new, retire_old]` "accept as-is" plans. `retire_old` stays required, and the contract gate and SQL guard are unchanged.
- **`staged.py`:** constants come from the scenario; generic data checks run for non-rename scenarios. The result adds `scenario`, `new_version` and `recommendation` (`accept_as_is | staged_rollout | reject`). A failed migrate records its stderr tail.
- **`checks.py`:**
  - `columns_agree` takes the column pair as a parameter
  - new `not_null` and `columns_after_contract`
  - new cases, added *after* `MANDATORY_AFTER_DEPLOY` is computed, so the rename scenario still runs its original 8: `old_write_old_read`, `old_create_old_read`, `new_create_plain_old_read`, `old_write_long_note`
  - internal op `create_plain` (not available to tester proposals)
  - cases that need new-app note access are recorded as **skipped** when the new version has no `note` field
- **`saleor_app.create_customer(..., include_note=True)`:** can leave out the note input.
- **`runner_api`:** an optional `scenario=` argument, only passed when given, so existing callers and test stubs are unaffected. The report adds `scenario` and `recommendation`.
- **`setup_env`:** builds a worktree for each `patches/<scenario>/<variant>/`. Missing patch folders are logged as `patch_missing`, not treated as errors.
- **`cli.py`:** `staged --scenario <id> --keep-db`.
- **Saleor patches:** `patches/<scenario>/<variant>/`, generated by `scripts/make_scenario_patches.py` from the pinned commit. The generator makes exact text edits (each must match once) and writes hand-written `0107_*` migrations. `.gitattributes` marks patch files `-text`.
- **Scripted plans and labels:** `proposals/scripted/<scenario>/*.json` and `proposals/manual/scenarios/*.json`. **Agents must not see these** (same rule as `plan_v2.json`).

## Round 2 additions (A5, D2, D4, D5, B2, B3, B4, A8)
- **New scenario fields:**
  - `old_version`: a scenario can ship its own old app, e.g. `raw-sql-rename/old` with a raw-SQL resolver
  - `prepare_sql`: legacy data created in the run DB only (B3 orphans)
  - `unchanged`: checks that pre-existing rows' values are not rewritten (B2, D4, D5)
  - `not_null_phases`: when required columns are checked
- **Plans:**
  - new stage kind `rollback_check`, placed after `deploy_new` and before `retire_old`. It migrates back to `0106`, checks note preservation and old-app smoke, then re-applies.
  - optional deploy `variant`, e.g. B4's `apply-reversible`
- **`saleor_app.gql`:** re-login and retry once on "Signature has expired". A WSL2 wall-clock jump of +1,573 s expired a fresh token mid-run. See the incident in `docs/results-scenarios.md`.
- **Bug fixed in my own refactor:** after deploy, the rename checks compared `note` and `customer_note` even when an immediate rename had already dropped `note`. They now only compare columns that exist.

## Decisions to review (Harsha)
1. **`apply` plans skip expand and contract.** This is what lets the tool say "safe as-is". The alternative would be a separate stage kind. I kept the plan schema small.
2. **Placeholder expand stages.** A3 and B1's safe plans need a no-op expand (`ALTER COLUMN note DROP NOT NULL`, already nullable), because `state_only` plans still require expand and contract. Should `state_only` plans be allowed without expand?
3. **The rename scenario's checks are untouched** (`rename_hooks`), even though they could now be expressed generically. That was done to guarantee identical results. Unify later if you prefer.
